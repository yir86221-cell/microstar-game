微动星瞳小组 AI 协作使用说明
适用对象：希望独立设计游戏、但不熟悉代码的小组成员
整理日期：2026 年 11 月 3 日

一、我们怎样一起修改

每个人使用自己的 GitHub 账号和自己的 AI 编程工具，连接同一个仓库，用中文说明想改的内容，让 AI 完成代码修改、预览和提交。组员可以直接设计并实现自己的部分，不需要负责人代为转述。

共同仓库：https://github.com/yir86221-cell/microstar-game
负责人：创建这个仓库的组员。
主分支：main。它保存全组目前确认采用的版本。
个人分支：每个人本次修改的工作版本，例如 feature/xiaowang-chick-dance。
Pull Request，简称 PR：请求把个人修改合并到主版本的页面，可以看改动、留言和讨论。
合并：将确认好的个人修改纳入全组主版本。

这套方式通过提交和合并同步代码，不是多人在同一页面上实时拖拽编辑。不同人的聊天记录和未提交修改不会自动互通。每个人都能发起设计和修改，合并可以由小组约定的轮值检查人负责，不必所有事都交给一位组员。

普通 AI 聊天窗口不一定能操作 GitHub。必须确认工具既能读取这个私有仓库，又能修改项目并推送代码；只能回答问题或读取资料的工具无法完成整个流程。复制仓库网址只是提供地址，不等于授权、克隆或同步成功。提示词不能代替登录授权，也不能凭空获得写入权限。

二、负责人先做一次的准备

1. 确认仓库已经设为 Private。
2. 确认上传页面的 Commit changes 已成功提交。回到 Code 页面，应能看到 dist 文件夹、scripts 文件夹、package.json、preview.mjs、README.md 等内容。
3. 若只看到 Quick setup 和命令提示，通常还是空仓库，请先完成上传提交。
4. 在 Settings → Collaborators → Add people 中输入成员的 GitHub 用户名，核对账号后发送邀请。
5. 成员接受邀请后才能获得协作权限。能打开试玩链接，不等于能访问或编辑私有代码仓库。
6. 约定谁改哪一部分，记录在 GitHub Issues 或 TASKS.md。例如：首页视觉、游戏菜单、小鸡关卡、小车关卡。可以各自设计，但两人同时改相同页面时要提前交流。

说明：初次网页上传的截图未显示 .github 和 .gitignore。游戏主要代码可先使用，协作模板与自动检查配置是否上传成功，需要在仓库中核对。没有 .github/workflows/check.yml 时，不应宣称 GitHub 已在自动检查每次提交；本机检查仍可由 AI 执行。

三、每位组员第一次接入

第 1 步：接受仓库邀请
登录自己的 GitHub，打开邀请邮件或 GitHub 通知，点击接受邀请。再打开上面的仓库网址，确认能看到文件。

第 2 步：选择能实际修改项目的 AI 工具
推荐在已有可用账号上使用 Codex 等 AI 编程工具。是否具备云端、写入和发布功能，取决于各自的账号、工作区和工具权限。组员应先完成能力检查，再开始设计，不要购买服务后才发现无法接入项目。

如果使用 Codex 云端，可参考以下官方流程，按钮以自己账号实际显示为准：
① 打开 Codex，新建任务。
② 在 Work in 中选择 Cloud，打开 Select environment，选择 Create environment。
③ 选择这个 GitHub 仓库；提示连接时，登录自己的 GitHub 并完成授权。
④ 如果仓库不在列表里，先核对已经接受邀请、授权账号正确、仓库访问范围已包含它。
⑤ 选择 Get started，让 Codex 读取仓库并准备运行环境。
⑥ 检查准备结果，完成所需确认后 Publish 环境；之后选择该环境开始任务。

这里的“发布环境”是保存可复用的开发环境，不等于把游戏网站公开上线。新任务可能从准备好的环境文件开始；因此每次修改前仍应让 AI 检查并同步 GitHub 最新 main。

如果使用本机 AI 编程工具，则打开或克隆这个仓库作为项目，再完成 GitHub 账号的读写授权。第一次是否需要下载由工具决定；不需要每次都重新下载，也不用手动打开每一个代码文件。

如果使用其他 AI，先发提示词 A。不要照抄 Codex 按钮去其他软件里寻找同名入口。涉及网页登录、验证码或授权时由本人完成，不把密码、验证码、Token 粘贴到聊天。

第 3 步：发送提示词 A，验证接入
AI 应当读取真实文件并告诉你当前分支、提交及项目内容。拿到证据后再发提示词 B 了解项目；不能读取时，按实际报错完成连接，不要让它另建一个同名网页冒充现有项目。

四、可直接复制给自己 AI 的提示词

【提示词 A　第一次接入仓库】

我是微动星瞳项目的一名组员，不会写代码。我要通过中文要求，独立修改我们已有的游戏 Demo。

团队私有仓库：
https://github.com/yir86221-cell/microstar-game

请先检查你目前是否具备读取私有 GitHub 仓库、编辑项目、执行检查、提交并推送分支的能力。不要因为我给了网址就说已经连接，也不要新建另一个项目替代它。

如果尚未授权，明确指出缺的是账号连接、仓库成员资格、仓库授权范围，还是工具本身没有写入能力。告诉我当前界面上下一步要做什么。登录和授权由我本人操作，不向我索要密码、验证码或访问令牌。

连接完成后：
1. 确认实际访问的是 yir86221-cell/microstar-game，并读取远端分支。
2. 在可用工作区检出项目；如果已有本地修改，先保留并说明情况，不要覆盖。
3. 读取 README.md、CONTRIBUTING.md、TASKS.md、package.json 和 dist 中的项目文件。若某文件缺失，请如实指出。
4. 从实际文件中核实首页、关卡、交互模式及运行方式。
5. 回复“已验证的仓库地址、当前分支、当前提交编号、实际读到的关卡名称、哪些操作权限尚未验证、下一步能怎样预览”。如果工具无法获得某项信息，说明原因，不编造。

这一步只接入和检查，不改游戏、不推送测试文件、不部署网站。不要声称本地已修改就等于 GitHub 已同步。

【提示词 B　让 AI 了解我们的设计】

请先实际读取团队仓库的当前代码，再协助我设计与实现。

项目叫“微动星瞳”，目前只做儿童游戏 Demo。视觉参考 EDA PLAY 的简洁、大图案、高饱和、黑底风格，页面结构与素材采用我们自己的设计。首页是吸引注意的黄色小鸡，下方文字为“点击或拍击来开始吧！”。点击或拍击后进入阶段选择。游戏左上角有暂停和菜单；菜单的关卡以大预览图和任务名称呈现，交互模式以较小按钮呈现。

重要约定：
- CVI Phase I、II、III 是阶段组织，拍击、精准点击、悬停是独立交互设置，不要混成一套等级。
- “悬停”指接触目标并持续停留，目前原型为 1.2 秒，不是隔空感应。
- 示意图统一为 1448×1086、4:3 横屏；实际网页应适配手机和平板，不拉伸图形。
- 当前四个示例任务是“让小鸡跳舞”“让小车开起来”“摘下红苹果”“点亮小星星”。请以当前仓库实际内容核对，不把这段说明当作最新代码证据。
- 本次不加入家长端、真实硬件和临床评分，不声称游戏成绩证明康复疗效。

正式项目原方案是《文字文稿(1).docx》。若仓库没有原方案，你就不能声称已经读过；遇到依赖原方案的新设计时，向我索取相应依据，先做不依赖它的部分。

请用简单中文说明现有结构和我可以修改的范围，等待我给出本次具体任务。

【提示词 C　开始自己的设计修改】

请在现有团队仓库上实现本次修改，我不会手写代码，希望由你完成实现与检查。

本次设计目标：［填写想改的页面或关卡］
期望效果：［写具体行为；可以附截图或草图］
验收标准：［写出我如何试玩确认效果］

开始前检查工作区是否有未提交修改，保护已有成果。获取 GitHub 最新 main，从最新主版本建立本次独立分支，分支名使用 feature/我的英文昵称-任务短名。不要直接修改远端 main，不强制推送，不覆盖别人的修改。

先给我一个简短的实现方案，随后完成明确范围内的修改。保持已经确认的首页、菜单及其他关卡正常。不要擅自重做整个项目或新增付费依赖。

完成后按 package.json 的真实脚本执行可用检查。项目原版提供 npm run check 和 npm test；脚本缺失时先报告原因。能够预览时给我可用预览入口，并说明是本机还是云端预览；不能预览时如实说明，不伪造试玩截图或检查结果。

这一步先留在个人分支，供我试玩和继续调整。不要自动合并到 main，不更新现有在线试玩网站。若本环境需要提交才能保留成果，可以提交本分支，但要明确是否已经推送到 GitHub。

例子：本次只调整“让小鸡跳舞”。有效拍击后，让小鸡左右摆动并轻轻跳一下；动画期间重复拍击不重复计数；暂停时动作与计时一起暂停。其他关卡和菜单布局保持原有行为。

【提示词 D　试玩满意后提交给小组】

我已经确认本次修改，可以提交给小组检查。

请确认当前是我的个人分支，检查本次改动范围与测试结果；如果 main 已有更新，在保留本次成果的前提下同步并处理冲突。存在设计取舍时说明冲突内容，不直接用一方整文件覆盖另一方。

将本次修改提交并推送到同一 GitHub 仓库的个人分支，然后创建面向 main 的 Pull Request。标题简明，正文说明改了什么、如何试玩、已通过和未完成的检查。不能创建 PR 时，给出已验证的分支链接和我需要点击的入口。

最后返回真实的提交编号、远端分支和 PR 链接。区分“只在本地保存”“已提交”“已推送”“已创建 PR”“已合并”。不要把完成一个步骤说成全部已完成。不要自动合并到 main，也不要自动部署网站。

【提示词 E　下一次接着做或接收组员成果】

我要继续微动星瞳项目。请先核对连接的是 https://github.com/yir86221-cell/microstar-game。

检查并保留当前未提交修改，获取 GitHub 最新 main，告诉我最近合并了哪些变化。如果我上次的任务仍未完成，请先说明本分支相对最新 main 的情况，再决定继续本分支还是建立新分支。不要删除旧成果，不要强制重置。

请从已核实的最新代码开始本次任务，不凭旧聊天或环境快照猜测最新版本。未合并的 PR 不自动算作团队主版本的一部分。

【提示词 F　负责检查合并的组员使用】

请检查这个 Pull Request：［粘贴 PR 链接］。

核对它与当前 main 的差异，阅读关联需求，检查变更是否限定在任务范围内、是否影响其他关卡或输入方式，并执行可用检查。能够预览时提供预览与试玩要点。

先告诉我：可以采用的改动、需要调整的问题、未验证的部分，以及是否有合并冲突。暂时不执行合并。等小组确认后，我会另行要求你合并指定 PR。

五、每次协作的一套固定动作

1. 在群里或 Issue 中认领任务，说明自己负责的页面或关卡。
2. 发提示词 E 同步最新版本；第一次接入先发 A 和 B。
3. 填好提示词 C，让自己的 AI 实现。
4. 自己试玩：返回、选关、三种操作、暂停、继续、完成反馈，以及手机和平板上的布局。
5. 满意后发提示词 D，取得 PR 链接并发给小组。
6. 另一位组员检查。需要修改时继续同一分支和 PR，不必重新发一份整个源码包。
7. 经小组确认后，由约定的检查人或负责人合并。
8. 其他组员下一次发提示词 E，从新 main 开始。

示例：A 修改小鸡动作，B 修改小车关卡。A 的分支不会立刻改变 B 的任务。A 合并后，B 让 AI 同步 main，才能取得 A 的已合并成果。两人改同一处出现冲突时，AI 可以帮助处理，但需要人决定采用哪种设计。

六、怎样知道是真的同步成功

AI 在本机或云端显示修改后的页面：说明这个工作版本已改变。
GitHub 出现个人分支及新提交：说明修改已上传。
GitHub 出现 Pull Request：说明已经发起合并请求。
PR 显示 Merged：说明修改进入团队主版本。
试玩网站出现新行为：还需要对相应代码版本完成网站发布。

GitHub 不会像多人在线文档一样自动合并所有未完成的设计，也不会自动同步聊天记录。第一次接入时即使采用同一云端环境，每个人仍需确认自己的 GitHub 权限与实际代码版本。

现有试玩网址：
https://microstar-play-loeev-1103.sizedpig.chatgpt.site

目前该网站与新建 GitHub 仓库尚未建立自动发布关系。代码上传、PR 合并、网站发布是三个不同状态。成员的个人预览可由其 AI 工具提供，但预览可用性取决于运行环境。127.0.0.1 或 localhost 是本机地址，发给其他人的电脑一般无法直接访问。

七、遇到这些问题怎么办

看不到私有仓库：先用本人 GitHub 账号在浏览器打开仓库，确认接受邀请；再检查 AI 连接的是否为同一个账号和正确的仓库范围。不要为了让 AI 看见而把仓库改成公开。

出现 404：可能是私有仓库未授权，也可能是地址错误。核对地址与登录账号，不能只凭 404 断定仓库不存在。

能读但不能修改或提交：检查 AI 工具是否只有读取能力、GitHub 是否授予写入权限。若工具不支持，不要让它假装已连接；换用具备项目修改能力的工具或完成必要接入。

AI 只给一段代码让我复制：明确告诉它“请在已连接的项目文件中实际修改，并提供可核验的结果”。如果它没有文件或仓库写入能力，应先解决工具接入。

提示合并冲突：将冲突页面交给自己的 AI 解释并处理，保留双方有效改动。不要删除重建整个仓库，不用旧 ZIP 覆盖全部文件。

主版本已经更新，但页面还是旧的：先分清打开的是个人预览还是已发布网站。同步 GitHub 不会自动刷新未接入发布流程的网站。

没有 Cloud 或环境选项：检查本人账号和工作区的功能是否可用。其他工具不要按 Codex 的按钮路径操作；请让它说明自身实际支持的接入方式。

GitHub 没有自动检查记录：核对 .github/workflows/check.yml 是否实际存在。即使没有这项配置，仍可让 AI 在自己的环境运行项目检查。当前使用说明不代表已经启用任何仓库权限规则、分支保护或自动部署。
